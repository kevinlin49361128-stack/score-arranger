背景與研究結論

起點你的想法：用 LLM 先把匯入的 PDF 清理成乾淨版本，再經預設演算法 (OMR) 匯入樂譜格式。

研究結論方向對一半，但順序反了。2025 實測 GPT-4o / Gemini / Claude 3 Opus 幾乎讀不出樂譜像素 → LLM 對「影像」是盲的，對「符號化樂譜」才會推理。所以 LLM 該放 OMR 之後做符號層校正，不是之前清影像。

既有決定2026-06-03 已決議「PDF/OMR 先保持現狀、不擴張」。核心價值是改編，曲庫已有 1103 首乾淨 MusicXML，PDF 只是入口而非產品本體。

⛔ 已排除（不需勾選）：「LLM 預清理影像 → 再 OMR」。LLM 碰像素會幻覺改音/加音/漏音，在 OMR 前就污染內容，違反「任何一步不准無中生有」。

1投資程度

要不要、以及投多少資源在 PDF/OMR 品質上？（單選）

A. 維持現狀，不動 零成本
保持 6/3 決定。Audiveris 照舊（乾淨印刷譜 80–90%），資源全放改編核心。
取捨：PDF 匯入體驗不變；手機拍照/掃描譜仍不好用，但那本來就不是主力場景。
B. 小投資：③ LLM 符號後校正層 🎯 建議 低
OMR 跑完後，讓 LLM 用調號 / 和弦進行 / 樂理合理性去修辨識錯誤。重用既有 harmony 分析 + LLM 整合 + OMR 糾錯 UI。
取捨：槓桿最高、不碰像素、風險低；但只能修「符號層說得通與否」，救不了 OMR 根本沒認出來的東西。
C. 中投資：B + homr 並列引擎 中
除了後校正，再把開源 homr（改良版 oemer，對拍照/掃描更穩）做成 Audiveris 的替代引擎選項，讓使用者依來源挑。
取捨：覆蓋拍照場景；但 homr 目前丟掉力度/演奏法/重升降，對乾淨印刷譜不見得贏 Audiveris → 是互補不是取代，且多一條相依與維運。
D. 大投資：換 end-to-end OMR 引擎 + 後校正 高
導入 Transformer 系 OMR（SMT++ / LEGATO 一脈）取代 Audiveris，全頁複音、層級更高。
取捨：天花板最高；但多為研究模型、整合與算力成本高、OMR 是焦油坑（最後 10–15% 錯誤最惱人），投報率不確定。與「核心是改編」的定位拉扯。
